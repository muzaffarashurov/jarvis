## 1. Executive Summary

Five capability-governance packages already exist in this repository, each independently complete and independently audited:

| Package | EP | Role |
|---|---|---|
| `src/core/capability/` | EP-069.4 | `Capability` domain model + `CapabilityRegistry` catalog + `CapabilityBackend` invocation contract |
| `src/core/capability_discovery/` | EP-069.5 | Task-text → ranked-candidate matching (`CapabilityDiscoveryEngine`) |
| `src/core/capability_security/` | EP-069.6 | Advisory risk assessment of one capability (`CapabilitySecurityEngine`) |
| `src/core/capability_policy/` | EP-070 | Deterministic policy-level decision from capability + assessment + lifecycle status (`PolicyEngine`) |
| `src/core/capability_lifecycle/` | EP-069.7 | Status/audit-trail tracking (ACTIVE/DISABLED/REVOKED) (`CapabilityLifecycleRegistry`) |

**VERIFIED:** none of the five is referenced by `src/bootstrap.py`, `src/core/command_router.py`, or `src/core/tool/*.py`, except `CapabilityRegistry` being test-only constructed (`grep` for `CapabilityRegistry()`/`CapabilitySecurityEngine`/`PolicyEngine`/`CapabilityLifecycleRegistry` across `src/` returns matches only inside each package's own directory and inside `docs/architecture/designs/JARVIS_DECISION_REQUIRED_ARCHITECTURE_RESOLUTION.md`'s own investigation). `bootstrap.py`'s only "capability"-named import is `CapabilityRegistryModule` (`src/skills/capability_registry/skill.py`, EP-056), an unrelated, pre-existing command module that composes `PluginService` and `CommandRouter.module_names` — it has zero dependency on the EP-069.4-.7/EP-070 stack. This confirms, independently, the same conclusion `EP069_5_DESIGN.md`'s own `__init__.py` docstring and `JARVIS_DECISION_REQUIRED_ARCHITECTURE_RESOLUTION.md`'s Decision 2 already recorded: **the five packages are individually correct and individually inert.**

A second, equally material fact, also independently reconfirmed this session: **`CapabilityRegistry` is never populated in production.** `CapabilityRegistry()` is constructed only inside `tests/EP069_4/` and `tests/EP069_5/`. No real capability — internal or otherwise — is registered anywhere `bootstrap.py` runs. `EP069_5_DESIGN.md`'s own `__init__.py` docstring names this explicitly as "the production `CapabilityRegistry` population gap identified during this EP's STEP 1 (nothing registers real capabilities today)," and states it was "deliberately not solved" by EP-069.5. It remains unsolved today.

This document's central conclusion: **EP-069.8 is not "connect four data-processing stages in sequence" — it is two smaller, separable pieces of wiring:**

1. A thin coordinator that calls `CapabilityLifecycleRegistry` → `CapabilitySecurityEngine` → `PolicyEngine` in sequence for one already-identified capability, and turns the resulting `PolicyDecision` into an allow/deny outcome. This is genuinely new code (the "missing piece" `JARVIS_DECISION_REQUIRED_ARCHITECTURE_RESOLUTION.md` already names), but it is composition, not redesign: it calls each engine's existing public method unchanged.
2. A resolution step at `CommandRouter.dispatch()` that decides, for a given `(module, action)` pair, whether a governed `Capability` exists at all. Because the catalog is empty today, this step's answer is "no" for every currently-registered command — meaning the coordinator, once wired, initially governs nothing, and every existing command continues to behave exactly as it does today. Only capabilities someone explicitly registers into `CapabilityRegistry` become subject to enforcement. This is the mechanism by which EP-069.8 stays an integration/wiring EP and does not silently redesign or expand the Capability catalog's population strategy, which is explicitly out of this EP's scope per `EP069.8_NUMBERING_DETERMINATION.md` §5.

The Discovery Engine (EP-069.5) is **not** part of this enforcement chain (see §5 and §6) — it solves a different problem (open-ended task-to-capability matching for Planning/Agent use) than `CommandRouter.dispatch()` has (an already-known, exact `(module, action)` target). This is a deliberate divergence from the illustrative sequence in the governing prompt and from the linear diagram in `JARVIS_DECISION_REQUIRED_ARCHITECTURE_RESOLUTION.md` §"Decision 2," justified in §5/§6 below.

## 2. Current Architecture

### 2.1 Command execution path (today)

`src/core/command_router.py`'s `CommandRouter.dispatch(raw_input: str)`:

1. Tokenizes `raw_input` (Windows-path-safe `shlex`, escape disabled).
2. Splits into `module_name, action, *arguments`.
3. Looks up `module_name.lower()` in `self._modules: dict[str, CommandModule]`.
4. If found, calls `module.execute(action, arguments) -> CommandResult` inside a blanket `try/except Exception`.
5. Returns the `CommandResult` (or a synthetic failure `CommandResult` for unknown module / parse error / internal exception).

`CommandRouter` has **no notion of capability identity at all** — VERIFIED by full read of `command_router.py` (195 lines): it imports nothing from `src.core.capability*`, and `dispatch()`'s only inputs are the raw string and its own `self._modules` dict. There is no `(module, action) → capability_id` mapping anywhere in the file, and no such mapping exists anywhere else in `src/` either (VERIFIED by repository-wide grep for `capability_id` outside the five packages' own directories/tests — zero matches).

`CommandModule` (a `Protocol`) is implemented by ~20+ Skill modules registered in `bootstrap.py::_build_command_router()` (`SystemModule`, `FileModule`, `BrowserModule`, `DesktopModule`, etc.). Each module owns its own namespace and interprets `action`/`arguments` however it likes; `CommandRouter` never inspects a module's internal behavior.

### 2.2 Tool Engine path (separate, today)

`src/core/tool/tool_engine.py`'s `ToolEngine` is a **different**, pre-existing execution path (EP-031), used by `ToolExecutionProvider` (EP-030) as a bridge from Plan Execution's `PlanStep`s — not from `CommandRouter.dispatch()`. `ToolEngine.invoke(tool_id)` / `invoke_for_step(subsystem, action)` look a `Tool` up in `ToolRegistry` and hand it to the currently selected `ToolProvider`. `Tool.handler` is a pre-bound, **zero-argument** callable (VERIFIED, `src/core/tool/tool.py` docstring and `EP069_4_DESIGN.md` §15.1's own worked example, re-confirmed this session).

These two paths — `CommandRouter.dispatch()` (arbitrary `list[str]` arguments, ~20+ Skill modules, the CLI/REST-API-facing surface) and `ToolEngine.invoke()` (zero-argument only, Plan-Execution-facing) — are **not the same chokepoint** and do not call each other. VERIFIED: no reference to `ToolEngine`/`ToolManager`/`ToolRegistry` exists in `command_router.py`, and no reference to `CommandRouter`/`CommandModule` exists in `tool_engine.py`. `EP051_DESIGN.md` (§"Parameter handling," re-confirmed this session) independently documents this exact split and its consequence: `Tool.handler`'s zero-argument limitation makes `ToolEngine` unusable for anything needing real arguments, which is why parameterized Skills (e.g. `browser`) are implemented as `CommandModule`s reached only through `CommandRouter.dispatch()`, never through `ToolEngine`.

### 2.3 Capability governance packages (today)

Each of the five packages is complete and independently unit-tested (`tests/EP069_4/`, `tests/EP069_5/`, `tests/EP069_6/`, `tests/EP069_7/`, `tests/EP070/`), but none is instantiated inside `bootstrap.py` or reachable from either execution path above. Detailed per-package interfaces are in §3.

## 3. Existing Governance Components

### 3.1 `Capability` model + `CapabilityRegistry` (EP-069.4) — `src/core/capability/`

- **Responsibility:** `Capability` (frozen dataclass) is the single catalog-entry type for internal tools, local CLI/GitHub-project tools, REST APIs, and browser-executed services. `CapabilityRegistry` is a thread-safe, in-memory, id-keyed catalog (`register`/`unregister`/`get`/`find`/`list`/`is_registered`). `CapabilityBackend` (ABC) is the not-yet-implemented invocation contract per `CapabilitySourceKind`.
- **Public interface:** `Capability.create(...)` (validating constructor), `CapabilityRegistry.{register, unregister, get, find, list, is_registered}`.
- **Dependencies:** none beyond stdlib.
- **Current integration status:** Not wired into `bootstrap.py`. `CapabilityRegistry()` is constructed only in `tests/EP069_4/` and `tests/EP069_5/`. Zero real capabilities are registered in production (VERIFIED, §1).
- **Exceptions:** `CapabilityError` (root), `CapabilityValidationError`, `CapabilityRegistryError`, `CapabilityNotFoundError`.

### 3.2 `CapabilityDiscoveryEngine` (EP-069.5) — `src/core/capability_discovery/`

- **Responsibility:** given a plain-text `task` description and a `CapabilityRegistry`, returns a ranked `CapabilityDiscoveryResult` (best-fit-first `CapabilityMatch` list) via its configured `CapabilityDiscoveryProvider`. Intended, per its own module docstring, as "the single decision point Planning/Agents can use instead of hard-coding 'which tool for which task'" — i.e. for **open-ended, fuzzy task→capability matching**, not for resolving an already-known, exact target.
- **Public interface:** `CapabilityDiscoveryEngine(provider=None).discover(task: str, registry: CapabilityRegistry, max_results=10, cost_hints=None) -> CapabilityDiscoveryResult`.
- **Dependencies:** `CapabilityRegistry` (read-only, via its public `list()` only), a `CapabilityDiscoveryProvider`.
- **Current integration status:** Not wired anywhere. Its own `__init__.py` explicitly names both facts §1 restates: production `CapabilityRegistry` is unpopulated, and it is "not integrated with Planning Engine, Agent Framework, or Tool Engine."
- **Exceptions:** `CapabilityDiscoveryError` (root), `CapabilityDiscoveryProviderError`.

### 3.3 `CapabilitySecurityEngine` (EP-069.6) — `src/core/capability_security/`

- **Responsibility:** advisory-only risk assessment of one `Capability`'s already-declared metadata (three deterministic checks in `DefaultCapabilitySecurityProvider`: missing provenance, trust/source mismatch, high-risk permission tag — all gated on `source_kind != INTERNAL`, so an `INTERNAL` capability can never trigger a finding). Returns a `CapabilitySecurityAssessment` (`overall_risk_level` + `findings`) that **carries no approve/reject field** — "advisory only" by explicit Owner Decision.
- **Public interface:** `CapabilitySecurityEngine(provider=None).assess(capability: Capability) -> CapabilitySecurityAssessment`.
- **Dependencies:** none beyond `Capability`; never queries `CapabilityRegistry` itself.
- **Current integration status:** Not wired into `bootstrap.py` or any execution path. Directly callable only.
- **Exceptions:** `CapabilitySecurityError` (root), `CapabilitySecurityProviderError`.

### 3.4 `PolicyEngine` (EP-070) — `src/core/capability_policy/`

- **Responsibility:** deterministic policy-level decision. `DefaultPolicyProvider.evaluate()` implements a fixed, ordered, first-match-wins six-row table (VERIFIED, re-read in full):
  1. `lifecycle_status == REVOKED` → `OBSERVE`
  2. `lifecycle_status == DISABLED` → `OBSERVE`
  3. `security_assessment.overall_risk_level == HIGH` → `REQUIRE_APPROVAL`
  4. `security_assessment.overall_risk_level == MEDIUM` → `PREPARE`
  5. `capability.source_kind != INTERNAL and security_assessment is None` → `ANALYZE`
  6. otherwise → `EXECUTE`

  **`OBSERVE` is explicitly documented, in the module docstring and in `PolicyLevel`'s own docstring, as a restrictive decision, never execution authorization.** Of the five `PolicyLevel` values, only `EXECUTE` represents "let this run now." `ANALYZE`/`PREPARE`/`REQUIRE_APPROVAL` all mean "do not execute as-is" under today's implementation, since no human-approval workflow, "analyze" workflow, or "prepare" workflow is implemented anywhere in the repository (UNVERIFIED beyond this: whether EP-071/072-era work will later give `REQUIRE_APPROVAL` a real approval flow; today none exists, so it can only be treated as a denial).
- **Public interface:** `PolicyEngine(provider=None).evaluate(capability, security_assessment=None, lifecycle_status=None) -> PolicyDecision`.
- **Dependencies:** none — `evaluate()`'s own signature already accepts an optional `CapabilitySecurityAssessment` and an optional `CapabilityLifecycleStatus` as plain, pre-fetched arguments; it never calls `CapabilitySecurityEngine` or `CapabilityLifecycleRegistry` itself (VERIFIED, both by import list and by the STEP 3 audit's own conformance table).
- **Current integration status:** `EP070_STEP3_AUDIT.md` confirms (audited PASS) zero `bootstrap.py`/`config.yaml`/CLI wiring, and the module docstring states it is "not connected to `ToolEngine`/`ToolExecutionProvider` or any execution path."
- **Exceptions:** `CapabilityPolicyError` (root), `CapabilityPolicyProviderError`.

### 3.5 `CapabilityLifecycleRegistry` (EP-069.7) — `src/core/capability_lifecycle/`

- **Responsibility:** thread-safe, in-memory status (`ACTIVE`/`DISABLED`/`REVOKED`) and append-only audit-trail tracker, independent of `CapabilityRegistry`. `REVOKED` is strictly terminal. No Provider/Engine/ABC framework here — Owner Decision: one correct set of transition rules, not a pluggable strategy.
- **Public interface:** `register(capability)`, `update(capability)`, `disable(capability_id, reason="")`, `enable(capability_id)`, `revoke(capability_id, reason)`, `status(capability_id) -> CapabilityLifecycleStatus` (**raises if untracked**), `history(capability_id)`, `is_tracked(capability_id) -> bool` (never raises).
- **Dependencies:** none — explicitly zero dependency on `CapabilityRegistry` (Owner Decision OD1); `disable()`/`revoke()` never touch the live catalog.
- **Current integration status:** Not wired anywhere; nothing calls `register()` in production, so nothing is tracked.
- **Exceptions:** `CapabilityLifecycleError` (root), `CapabilityLifecycleNotFoundError`, `CapabilityLifecycleConflictError`, `CapabilityLifecycleValidationError`.

## 5. Governance Gap

The gap is precisely: **a fully correct, fully audited four-package decision pipeline exists (Security → Policy, with Lifecycle as an input to Policy), but nothing calls it, and nothing tells it which `Capability` to evaluate for a given user action, because `CommandRouter.dispatch()` never resolves a `(module, action)` pair to a `Capability` at all.**

This has two independent causes that must not be conflated:

1. **No caller.** `PolicyEngine.evaluate()`, `CapabilitySecurityEngine.assess()`, and `CapabilityLifecycleRegistry.status()` are each individually correct and individually callable, but no production code calls them in sequence for a real dispatch. This is what a coordinator (§6/§10) solves.
2. **No catalog data.** Even with a coordinator wired into `CommandRouter.dispatch()`, it has nothing to evaluate unless a real `Capability` has been registered into `CapabilityRegistry` for that `(module, action)`, and today none are. This is a **data-population** gap, not a **wiring** gap — and per `EP069.8_NUMBERING_DETERMINATION.md` §5's own scope boundary, EP-069.8 owns wiring the five packages into "at least one genuine execution path," not building a new capability-catalog-population mechanism for every existing Skill module. §13 (Backward Compatibility) explains why this is the correct, safe default rather than a deferred problem: an unresolved capability must mean "ungoverned, behave exactly as today," not "block everything," or EP-069.8 would silently disable the entire command surface on day one — a far larger, unauthorized change of behavior than an integration EP should make.

A third, related but structurally already-solved point: `EP069_5_DESIGN.md`'s own `__init__.py` and `JARVIS_DECISION_REQUIRED_ARCHITECTURE_RESOLUTION.md`'s Decision 2 already name the population gap; this document does not discover it, only reconfirms it and states its consequence for EP-069.8's scope explicitly (§9, §13, §18).

## 6. Proposed Integration Architecture

**CURRENT** (repeated from §4 for contrast):

```
CommandRouter.dispatch(raw_input) → module.execute(action, arguments) → CommandResult
```

**PROPOSED:**

```
CommandRouter.dispatch(raw_input)
        │  tokenize -> (module_name, action, arguments)   [UNCHANGED]
        ▼
self._modules[module_name.lower()]   ── not found ──▶ CommandResult(success=False, ...)  [UNCHANGED]
        │  found
        ▼
[NEW] resolve capability_id for (module_name, action)
        │
        ├── no Capability registered for this id ──▶ (ungoverned — proceed exactly as CURRENT)
        │
        └── Capability found ──▶ [NEW] CapabilityGovernanceCoordinator.authorize(capability_id)
                                          │
                                          ▼
                                  CapabilityRegistry.find(capability_id)   [EP-069.4, unchanged]
                                          │  not found (race/inconsistent catalog) ──▶ deny, log
                                          ▼
                                  CapabilityLifecycleRegistry.is_tracked()/.status()  [EP-069.7, unchanged]
                                          │  (untracked → lifecycle_status=None; tracked → real status)
                                          ▼
                                  CapabilitySecurityEngine.assess(capability)  [EP-069.6, unchanged]
                                          │
                                          ▼
                                  PolicyEngine.evaluate(capability, assessment, lifecycle_status)  [EP-070, unchanged]
                                          │
                            ┌─────────────┴─────────────┐
                     level == EXECUTE            level != EXECUTE
                            │                             │
                            ▼                             ▼
                 CapabilityLifecycleRegistry      CapabilityLifecycleRegistry
                 (best-effort audit event,        (best-effort audit event,
                  "authorized")                    "denied: <level>, <reasons>")
                            │                             │
                            ▼                             ▼
                 module.execute(action, args)     CommandResult(success=False,
                 [UNCHANGED call]                    message naming the PolicyLevel/reason)
```

Distinguishing CURRENT from PROPOSED precisely: `CommandRouter.dispatch()`'s tokenizing, module lookup, `module.execute()` call, and exception handling are **byte-for-byte unchanged**. The only new behavior is a resolution + authorization step inserted **before** `module.execute()` is reached, active only for `(module, action)` pairs that resolve to a registered `Capability`.

## 8. CommandRouter Integration

**Conceptual change only — not implemented in STEP 1.**

- `CommandRouter.dispatch()` gains one new step, inserted after module lookup succeeds and before `module.execute()` is called.
- **What information is available at dispatch time:** `module_name` (lowercased), `action` (lowercased or empty), `arguments` (`list[str]`). No capability identity is available today (VERIFIED §2.1) — it must be derived.
- **Whether the router already has access to capability identity:** No.
- **Whether command → capability resolution already exists:** No — confirmed by full read of `command_router.py` and repository-wide grep (§2.1). This resolution step is new.
- **Where governance should be invoked:** After module lookup (so an "unknown module" response is unaffected — it is not a governance question), **before** `module.execute()` (so a denial never reaches a handler's side effects). Governance must not run before module lookup, since it would then need to authorize actions for modules that do not even exist.
- **How denial should stop execution:** By returning a `CommandResult(success=False, ...)` directly from `dispatch()`, exactly mirroring the existing "Unknown module" / "Internal error" early-return pattern already in the method — no exception propagates out of `dispatch()` for a denial, matching the method's own documented contract ("a module must never crash the shell").
- **Whether `dispatch()` needs a new coordinator/service abstraction:** Yes — a `CapabilityGovernanceCoordinator` (new, small class; see §10), injected into `CommandRouter`'s constructor, not built by `CommandRouter` itself (mirrors the existing dependency-injection pattern `bootstrap.py::_build_command_router()` already uses for every other collaborator). `CommandRouter` itself must not import `CapabilityRegistry`/`CapabilitySecurityEngine`/`PolicyEngine`/`CapabilityLifecycleRegistry` directly — it depends on exactly one new seam.

## 9. Tool Engine Integration

**Not required for EP-069.8**, for two independent reasons, both confirmed this session:

1. **Different chokepoint, same conclusion as `EP051_DESIGN.md`'s own already-documented finding:** `ToolEngine` is reached only from `ToolExecutionProvider`/Plan Execution, never from `CommandRouter.dispatch()` (§2.2). A capability resolved and authorized at `CommandRouter.dispatch()` says nothing about a `Tool` invoked via `ToolEngine.invoke_for_step()` from a `Plan` — that is a structurally separate call path with no shared call frame.
2. **Zero-argument-handler limitation is a Tool Engine constraint, not a governance constraint.** It affects what *arguments* a `Tool.handler` can receive; it does not affect whether the *identity* of the capability being invoked can be authorized. Nothing about wiring the five governance packages requires widening `Tool.handler`'s signature, and this document does not propose doing so — that would be exactly the kind of scope expansion the calling task prohibits ("Do NOT silently expand Tool Engine scope unless the existing architecture proves that it is necessary").

**Consequence:** actions reachable only via `ToolEngine`/Plan Execution remain ungoverned after EP-069.8. This is an explicit, named scope boundary (§17), not an oversight — extending governance to that path is future work, contingent on Tool Engine gaining a real per-tool identity/argument model, which multiple existing design docs (`EP051_DESIGN.md`, `EP055_DESIGN.md`, `EP056_DESIGN.md`) already independently flag as blocked on the same zero-argument limitation for unrelated reasons.

## 10. Dependency / Wiring Model

**New component (conceptual, STEP 2 scope): `CapabilityGovernanceCoordinator`**

- Lives in a new module, e.g. `src/core/capability_governance/capability_governance_coordinator.py` (naming mirrors the existing one-concept-per-package convention every EP-069.x/EP-070 package already follows — a new sibling package, not code added inside any of the five existing ones, per the constraint "do not redesign EP-069.6/.7/070").
- Constructor takes the four existing components as already-constructed collaborators (dependency injection, not internal construction) — mirrors `RuntimeService`'s own existing constructor pattern of accepting already-built services:

  ```
  CapabilityGovernanceCoordinator(
      capability_registry: CapabilityRegistry,
      security_engine: CapabilitySecurityEngine,
      policy_engine: PolicyEngine,
      lifecycle_registry: CapabilityLifecycleRegistry,
  )
  ```

- Single public method (exact name/signature an Owner Decision for STEP 2; conceptually): `authorize(capability_id: str) -> GovernanceDecision`, where `GovernanceDecision` wraps the resulting `PolicyDecision` plus a resolved boolean "may execute" (`level == PolicyLevel.EXECUTE`) — this boolean-collapse is new code (it does not exist in `PolicyLevel`/`PolicyDecision` themselves, correctly, per Owner Decision OD6's explicit "no ordering" rule), and belongs in the coordinator, not in `PolicyDecision` itself, so `capability_policy_result.py` remains unmodified.
- `bootstrap.py::initialize()` constructs one `CapabilityRegistry`, one `CapabilitySecurityEngine`, one `PolicyEngine`, one `CapabilityLifecycleRegistry`, and one `CapabilityGovernanceCoordinator` wrapping them, then passes the coordinator into `CommandRouter`'s constructor (a new, optional constructor parameter — see §13). This is the **only** new wiring inside `bootstrap.py`; none of the four underlying engines' own construction changes from how their own design docs already describe them being constructed in tests.
- The `(module, action) → capability_id` resolution itself (§8) is a **separate, smaller concern** from the coordinator — the coordinator only ever receives an already-resolved `capability_id` (or is not called at all). Where that resolution logic lives (inside `CommandRouter` itself vs. a small lookup table owned by `bootstrap.py` and injected alongside the coordinator) is an open STEP 2 design choice (§17); either way it is plain data, not new governance logic.

## 11. Governance Decision Flow

For one dispatched `(module, action)` pair that resolves to a registered `capability_id`:

1. `CapabilityRegistry.find(capability_id)` → if `None` (should not happen if resolution in §8/§10 is internally consistent, but the catalog and the resolution table are two separate data structures that could drift), treat as **deny**, log at `ERROR` (an inconsistency, not a normal governance outcome).
2. `CapabilityLifecycleRegistry.is_tracked(capability_id)` → if `False`, `lifecycle_status = None` (an unregistered-in-lifecycle capability is not `REVOKED`/`DISABLED`, so Policy rules 1/2 correctly do not fire for it); if `True`, `lifecycle_status = CapabilityLifecycleRegistry.status(capability_id)`.
3. `CapabilitySecurityEngine.assess(capability)` → `security_assessment` (always succeeds for a well-formed `Capability`; the only documented failure is a `None` capability, which cannot occur here since step 1 already returned a non-`None` value).
4. `PolicyEngine.evaluate(capability, security_assessment, lifecycle_status)` → `PolicyDecision`.
5. If `PolicyDecision.level == PolicyLevel.EXECUTE`: authorize. Record a lifecycle audit event (see open question, §17) and proceed to `module.execute()`.
6. Otherwise (`OBSERVE`/`ANALYZE`/`PREPARE`/`REQUIRE_APPROVAL`): deny. Record a lifecycle audit event and return a denial `CommandResult` naming the `PolicyLevel` and `PolicyDecision.reasons`, without calling `module.execute()`.

This is a straight-line sequence, not a fan-out — matching `JARVIS_DECISION_REQUIRED_ARCHITECTURE_RESOLUTION.md` Decision 2 item 2's own recommendation ("centralized... not distributed across each skill/module individually").

## 12. Error and Denial Semantics

Following the constraint "do not invent arbitrary exception names" and "use existing project conventions where possible":

- **Capability unknown** (no `Capability` registered for the resolved `capability_id`, or resolution finds no `capability_id` for this `(module, action)` at all): **not a denial** — this is the ungoverned/backward-compatible path (§6, §13). No exception, no special `CommandResult`; `dispatch()` proceeds exactly as it does today.
- **Capability found but `CapabilityRegistry.find()` inconsistency** (§11 step 1): deny; use the coordinator's own new, narrowly scoped exception or a plain deny result — an Owner Decision for STEP 2 whether this surfaces as a raised exception (caught by `CommandRouter`'s existing blanket `except Exception` in `dispatch()`, which already turns any module-side exception into `CommandResult(success=False, "Internal error...")`) or as a `GovernanceDecision` carrying its own denial reason. Either reuses an existing pattern; no new top-level exception hierarchy is required beyond, at most, one new root (e.g. `CapabilityGovernanceError`) mirroring every existing package's own single-root convention (`CapabilityError`, `CapabilityDiscoveryError`, `CapabilitySecurityError`, `CapabilityPolicyError`, `CapabilityLifecycleError`).
- **Capability disabled / revoked:** `PolicyEngine` already returns `OBSERVE` for both (§3.4) — the coordinator treats any non-`EXECUTE` level as deny (§11 step 6). No new logic is needed to special-case `DISABLED` vs. `REVOKED` differently; `PolicyDecision.reasons` already carries the distinguishing human-readable text.
- **Security denies access:** there is no "security denies" concept as such — `CapabilitySecurityEngine` never denies (§3.3); a `HIGH`/`MEDIUM` assessment flows into `PolicyEngine`, which is the sole component that turns it into a restrictive `PolicyLevel` (`REQUIRE_APPROVAL`/`PREPARE`). The coordinator must not shortcut this by reading `security_assessment.overall_risk_level` directly and denying itself — doing so would duplicate `PolicyEngine`'s own rule table outside `PolicyEngine`, which the constraints explicitly forbid ("do not duplicate capability governance logic").
- **Policy denies access:** any `PolicyDecision.level != PolicyLevel.EXECUTE` (§11 step 6).
- **Lifecycle state prevents execution:** subsumed by Policy rules 1/2 (`REVOKED`/`DISABLED` → `OBSERVE`) — the coordinator does not need its own separate lifecycle-denial branch; it is already fully expressed through `PolicyDecision`.
- **Handler/tool missing:** unrelated to governance — this remains `CommandRouter`'s existing "Unknown module" path (§8), evaluated before governance runs, unchanged.
- **Internal governance error** (e.g. `CapabilitySecurityEngine`/`PolicyEngine` raises unexpectedly): the coordinator must not let this crash `dispatch()`. `CommandRouter.dispatch()`'s existing blanket `except Exception` around `module.execute()` already establishes the project's convention ("a module must never crash the shell" — `command_router.py`'s own docstring). The coordinator call should be wrapped the same way, and a governance-engine exception should **fail closed** (deny), not fail open — this is a deliberate security-boundary choice (§15), distinct from `module.execute()`'s own exception handling, which fails to an error message but does not need to fail either open or closed since the action already ran.

## 13. Backward Compatibility

- **Existing public APIs:** `CommandRouter.dispatch(raw_input: str) -> CommandResult` signature is unchanged. `CommandRouter.register()`/`register_modules()`/`module_names` are unchanged. `CommandModule` protocol is unchanged.
- **Existing constructor expectations:** `CommandRouter()` currently takes no arguments (VERIFIED, `__init__`). Adding a coordinator dependency must not break every existing `CommandRouter()` call site (`bootstrap.py`, and any test that constructs a bare `CommandRouter()` directly). **DECISION:** the new coordinator parameter must be optional, defaulting to `None` (meaning "no governance configured — behave exactly as today, unconditionally"), exactly mirroring how every other optional collaborator in this codebase (e.g. `CapabilityDiscoveryEngine(provider: ... | None = None)`) is threaded through as an optional constructor argument with a safe default.
- **Bootstrap assumptions:** `bootstrap.py::_build_command_router()` is the only production call site that constructs a real `CommandRouter`; it gains new construction of the four engines plus the coordinator, then passes the coordinator in. No other existing construction in `_build_command_router()` changes.
- **Tests that may depend on current behavior:** every existing test that constructs `CommandRouter()` bare (no coordinator argument) must continue to pass unmodified, since the default is "no governance." `tests/EP069_4/`, `tests/EP069_5/`, `tests/EP069_6/`, `tests/EP069_7/`, `tests/EP070/` each construct their own package's classes directly and are unaffected by this EP, since none of those packages' own code changes.
- **Compatibility risk — the empty-catalog default:** because `CapabilityRegistry` starts empty and nothing in this EP's scope populates it with real, production capabilities (§5), **every existing command remains fully ungoverned immediately after this EP ships**, by construction, not by omission. This is the correct backward-compatibility behavior for an integration/wiring EP — but it also means EP-069.8 alone delivers no functional enforcement of any real command until a follow-on step (explicitly out of this EP's scope, §18) registers real `Capability` entries for at least one existing `(module, action)` pair. This should be stated plainly to the Owner rather than implied.

## 14. Configuration Impact

Per the constraint "do not introduce configuration merely because it seems convenient," and given the empty-catalog default already makes the entire chain inert by default (§13), a config flag is not strictly required for STEP 2 to be safe. However, this repository has an established, uniform convention — every subsystem in `config/config.yaml` (`memory`, `personal_data`, `discord`, `email`, etc.) exposes its own `enabled: true|false` (VERIFIED, §-level grep across `config/config.yaml`). **RECOMMENDATION, not a requirement:** a `capability_governance.enabled` (default `true`, since the catalog-empty default already makes it a no-op) flag would let an operator disable the coordinator call entirely (e.g. during an incident) without needing to also empty the catalog — this is the same "opt-out, not opt-in" posture every other subsystem in `config.yaml` already uses. This is flagged as an **Owner Decision** for STEP 2, not assumed here, per the constraint against introducing configuration speculatively.

No other configuration change is required: `PolicyEngine`/`CapabilitySecurityEngine`/`CapabilityLifecycleRegistry` each already default to their own deterministic, no-config `Default*Provider` — nothing about wiring them requires new tunables.

## 15. Security Considerations

**Enforcement boundary:** the sole point where an unauthorized capability must be prevented from reaching executable code is inside `CommandRouter.dispatch()`, immediately before the `module.execute()` call (§8) — this is the single chokepoint every CLI/REST-API-facing interface already shares (`InteractiveShell` and `ApiRouter` both call `CommandRouter.dispatch()`, VERIFIED via `bootstrap.py`'s own construction of both against the same `router` instance). This satisfies the constraint "the architecture must not rely on callers voluntarily invoking governance checks": once wired, every dispatch through this one method is subject to the resolution/authorization step, structurally, not by convention — no individual `CommandModule` can opt out, because the check happens in `CommandRouter` itself, not inside any module's own `execute()`.

**Bypass risks, named explicitly:**
1. **The `ToolEngine`/Plan-Execution path remains entirely ungoverned** (§9) — an action reachable only through a `Plan`/`ToolEngine.invoke_for_step()` and never through `CommandRouter.dispatch()` is not covered by this EP. This is the most significant named residual risk, and it is a scope boundary, not an oversight (§9, §17).
2. **Fail-open on coordinator internal error must be explicitly avoided** (§12) — an exception raised inside `CapabilitySecurityEngine`/`PolicyEngine`/`CapabilityLifecycleRegistry` while evaluating a *registered* capability must **deny**, not silently fall through to execution; this is the one place this document deliberately departs from `module.execute()`'s own "log and continue" exception convention, because the risk profile is different (a broken handler failing safely for its own user vs. a broken governance check silently granting access).
3. **Catalog/resolution-table drift** (§11 step 1) — if the `(module, action) → capability_id` resolution table and `CapabilityRegistry`'s actual contents disagree (e.g. a capability_id resolves but was never registered), the coordinator must deny, not skip governance, since skipping would be indistinguishable from the "ungoverned" path.
4. **The empty-catalog default is a real, intentional weakness on day one** (§13) — restated here because it is a security-relevant fact, not just a compatibility one: shipping this EP alone changes nothing about what is actually preventable, only what becomes preventable once capabilities are registered.

## 16. Testing Strategy

STEP 1 writes no tests. STEP 2 must verify, at minimum:

- **Positive execution:** a registered, `ACTIVE`, `INTERNAL`, no-findings capability reaches `EXECUTE` and `module.execute()` is actually called.
- **Unknown capability (ungoverned path):** a `(module, action)` with no resolvable `capability_id` behaves identically to `CommandRouter` today (regression-style, byte-for-byte `CommandResult` comparison against pre-EP-069.8 behavior for at least one existing module/action).
- **Security denial:** an externally sourced capability with a high-risk `required_permissions` tag or a `TRUSTED_INTERNAL`/non-`INTERNAL` mismatch reaches `REQUIRE_APPROVAL` and is denied.
- **Policy denial (non-security-driven):** a non-`INTERNAL` capability with no assessment supplied is denied at `ANALYZE` — exercising the coordinator's obligation to always supply an assessment (this case should not be reachable if the coordinator always calls `CapabilitySecurityEngine.assess()`, but the underlying rule must still be exercised via a `PolicyEngine`-level test).
- **Lifecycle denial:** a `DISABLED` and, separately, a `REVOKED` capability are both denied (`OBSERVE`), including via the coordinator's own `is_tracked()`/`status()` sequencing, and untracked capabilities are confirmed to pass `lifecycle_status=None` rather than raising.
- **Successful execution audit trail:** an `EXECUTE` outcome results in a lifecycle event being recorded (contingent on §17's open question being resolved).
- **Regression behavior:** every pre-existing `CommandRouter`/Skill-module test continues to pass unmodified with no coordinator configured (`CommandRouter(coordinator=None)` / default).
- **Integration-level enforcement:** an end-to-end test constructing a real `bootstrap.py`-style wiring (or a test-scoped equivalent) confirms a denied capability's side effects genuinely do not occur (e.g. a `DISABLED` capability's underlying module method is confirmed via a spy/mock to never be called).
- **Bypass attempts:** confirm there is no code path by which a `CommandModule.execute()` can be reached for a registered, non-`EXECUTE` capability other than a direct, out-of-band call to the module object itself (which is outside `CommandRouter`'s own control by design, and out of scope for this EP — see §17).

## 17. Risks and Open Questions

**Confirmed facts** (re-verified this session, not merely cited):
- `CommandRouter.dispatch()` has no capability-identity concept today.
- No `(module, action) → capability_id` mapping exists anywhere in the repository.
- `CapabilityRegistry` is never populated in production.
- `PolicyEngine.evaluate()`'s signature already accepts everything the coordinator needs to supply.
- `ToolEngine`/Plan Execution is a structurally separate path from `CommandRouter.dispatch()`.
- `CapabilitySecurityEngine` never produces a `HIGH`/`MEDIUM` finding for an `INTERNAL` capability.

**Design decisions this document makes** (proposed, not yet Owner-approved):
- A new `CapabilityGovernanceCoordinator` is the right (and only) new abstraction; no changes to any of the five existing packages.
- The coordinator is optional/injectable into `CommandRouter`, defaulting to inert, to preserve backward compatibility unconditionally.
- Discovery Engine (EP-069.5) is excluded from this chain (§6, §9) as solving a different problem.
- Any non-`EXECUTE` `PolicyLevel` is treated as a denial for `CommandRouter.dispatch()` purposes, since no approval/analyze/prepare workflow exists to act on the alternative otherwise.
- Governance-engine internal errors fail closed.

**Assumptions:**
- `CapabilityLifecycleRegistry.status()`'s raise-if-untracked behavior is intentionally handled via `is_tracked()` first, not caught as an exception, matching the class's own documented pattern of exposing `is_tracked()` precisely so callers can avoid the raising path (VERIFIED from the docstring: "Never raises").
- `REQUIRE_APPROVAL` has no implemented approval mechanism anywhere in the repository today (UNVERIFIED beyond a repository-wide search finding none); treating it as a hard denial, rather than e.g. queuing for later approval, is the only behavior consistent with "do not invent" new mechanisms in an integration EP.

**Unresolved questions for the Owner (STEP 2 must not guess these):**
1. **Where does the `(module, action) → capability_id` resolution table live**, and who populates it? (§10, §11) — inside `CommandRouter` as a small injected dict, inside `bootstrap.py` alongside the coordinator, or as a method each `CommandModule` optionally implements? This determines how future capabilities get registered and is the largest remaining design surface STEP 2 must resolve; this document deliberately does not pick one, since picking incorrectly here risks exactly the "expand scope" or "invent unnecessary abstraction" failure modes the constraints warn against.
2. **How should a successful `EXECUTE` outcome be recorded in `CapabilityLifecycleRegistry`?** The registry's current public API (`register`/`update`/`disable`/`enable`/`revoke`) has no generic "record an arbitrary audit event" method distinct from a status transition — an `EXECUTE` authorization is not a status transition. Whether this requires a small, additive method on `CapabilityLifecycleRegistry` (which would be a change to an EP-069.7 file, requiring care not to violate "do not redesign EP-069.7") or whether audit logging for successful executions should instead go through the existing `loguru` logger only (no `CapabilityLifecycleRegistry` involvement for the success path, only for actual lifecycle transitions) is unresolved. **RECOMMENDATION:** the latter (logger only for `EXECUTE`; `CapabilityLifecycleRegistry` stays exactly as it is) is more consistent with "avoid duplicate sources of truth" (§ Single Source of Truth) and avoids touching an already-audited package.
3. **Is a `capability_governance.enabled` config flag actually wanted** (§14), or is the empty-catalog default considered sufficient safety on its own?
4. **What is the intended default `PolicyLevel`/trust posture for the first capabilities someone registers** — this is explicitly named as unresolved in `JARVIS_DECISION_REQUIRED_ARCHITECTURE_RESOLUTION.md`'s own "REMAINING OWNER DECISIONS" list ("permissive-by-default (OBSERVE) vs. restrictive-by-default (REQUIRE_APPROVAL)") and is unchanged by this document — it is a data/registration-time decision, not a wiring decision, and is out of EP-069.8's scope regardless.
5. **Should `REQUIRE_APPROVAL` remain a hard denial indefinitely**, or is a future EP (EP-071/072-adjacent) expected to give it a real approval workflow that this coordinator's design should not preclude? This document's design (treat as denial) does not preclude a later change — `GovernanceDecision` wrapping `PolicyDecision` rather than collapsing it to only a boolean at the `PolicyEngine` layer keeps the door open — but the Owner should confirm this is the intended posture.
