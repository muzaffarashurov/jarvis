## 1. EXISTING EP OWNERSHIP

**NO — new EP number required. No existing EP owns this exact responsibility.**

Evidence:

- A repository-wide search for `governance`, `wiring`, `enforcement chain`, `capability registry` + `integration`, and `EP-069.8`/`EP-070.1` returns **no EP title, design document, or backlog entry** describing "connect capability discovery/security/policy/lifecycle into one enforcement chain."
- `JARVIS_ROADMAP.md`'s own Phase A text is explicit about what each already-numbered item in this range covers: *"EP-069–EP-074. Provider/tool registry, policy & human-approval engine, credential management, autonomous-execution safety boundaries, browser automation with human-in-the-loop, and an autonomous project/EP orchestrator."* Mapped to numbers (confirmed against each item's own design/audit doc where one exists):
  - EP‑070 = policy & human-approval engine (**already built** — this is the Policy Engine itself, not an integration of it with anything else).
  - EP‑071 = credential management.
  - EP‑072 = autonomous-execution safety boundaries.
  - EP‑073 = browser automation with human-in-the-loop.
  - EP‑074 (+EP‑074.1) = autonomous project/EP orchestrator.
  - None of these is "wire the already-built EP‑069.4–.7/EP‑070 components to each other and to a real execution path."
- `EP069_4_DESIGN.md`'s own scope statement (re-confirmed): EP‑069.4 shipped with **zero concrete backend implementations**, explicitly deferring discovery (.5), security (.6), and lifecycle (.7) — but never claiming any of .4–.7 would later wire themselves together. Each of EP‑069.5/.6/.7's own design docs independently and explicitly disclaims integration with the others and with `bootstrap.py`/`CommandRouter` (by Owner Decision, in each doc).
- `JARVIS_ROADMAP.md`'s own text describing EP‑069.6/.7 states they were built *"needed for Jarvis to eventually use local GitHub projects/CLI tools, external APIs, external web services, and browser-only services as capabilities"* — i.e., the roadmap already anticipates further work is needed before these are actually usable, without assigning that further work a number.

**Conclusion:** this is a genuinely new engineering boundary, not covered by EP‑070, EP‑071, EP‑072, EP‑073, EP‑074, or any sub-package of EP‑069 that currently exists.

## 3. OFFICIAL EP NUMBER

`EP-069.8`

**Why not a fresh top-level number (e.g., the next unused number after Phase N's EP‑140):** the repository's phase-based numbering groups EPs thematically, not just sequentially; a top-level number far outside Phase A would sever this EP's evident dependency relationship to EP‑069.4–.7 in the roadmap's own organizing scheme, for no benefit.

**Why not EP‑070.1:** the work's dependency scope spans EP‑069.4, EP‑069.5, EP‑069.6, EP‑069.7, *and* EP‑070 — it is not owned by EP‑070 alone (EP‑070 is only one of five components being wired together). EP‑069's own family already carries the "Capability" naming and already contains the four packages (.4–.7) that make up the bulk of what is being connected; EP‑070 is consumed by this work exactly as EP‑069.4–.7 are, not the parent it extends.

**Why EP‑069.8 does not conflict with the roadmap's "two remaining sub-packages" language:** `JARVIS_ROADMAP.md` currently states EP‑069 "now also carries two remaining planning-only sub-packages (EP‑069.6–EP‑069.7)" — at the time that sentence was written. This is a **description of the roadmap's then-current state**, not a hard ceiling the repository's own numbering rules impose (no numbering-policy document found anywhere states EP‑069 is capped at seven sub-packages). The same document's EP‑074.1 precedent shows new sub-packages are added to an existing EP number precisely when new scope is identified after the fact. Updating that sentence to also mention EP‑069.8 is a documentation action for a future roadmap edit, not a numbering conflict today.

## 5. SCOPE BOUNDARY

**Owns:** connecting the already-implemented, already-audited EP‑069.5 (Discovery) → EP‑069.6 (Security) → EP‑070 (Policy) → EP‑069.7 (Lifecycle) chain into one real coordinator, and wiring that coordinator into `bootstrap.py` and at least one genuine execution path (the enforcement point, primarily `CommandRouter.dispatch()`).

**Explicitly does NOT own** (confirmed against the prior architecture analysis, unchanged here):
- A new Capability Registry, Discovery engine, Security engine, Policy engine, or Lifecycle registry — all five already exist and are not redesigned.
- MCP implementation — a separate future `CapabilityBackend`, dependent on this EP but not part of it.
- Resource/Cost Governance — separate future EP.
- Diagnostics or Observability — separate future EPs.
- Task DAG or Typed Artifacts — unrelated orchestration concern.
- Self-development/EP‑074 — a separate, still-blocked future EP that consumes this one's output.
- External Data Integration — unrelated concern (Decision 1 of the prior analysis).

This is confirmed as an **integration/wiring EP**, not a redesign: every one of EP‑069.4/.5/.6/.7/EP‑070's own already-audited internal logic is reused unmodified; only a new coordinator and its wiring into `bootstrap.py`/`CommandRouter` are new code.
