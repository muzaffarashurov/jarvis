# EP069.8 — STEP 1.1 — Capability Governance Integration — Architecture Resolution

**Type:** Read-only architecture-resolution report. No production code, test, configuration, `bootstrap.py`, `command_router.py`, or any other source file was created, modified, or deleted in the course of this session. No Git command was run.

**Epistemic labels used throughout:** `VERIFIED` (read directly from source this session), `INFERENCE` (conclusion drawn from combining verified facts), `DECISION` (this report's own architectural choice), `UNVERIFIED` (could not be confirmed from the repository).

---

## 1. Executive Decision

**Decision:** `(module_name, action_name) → capability_id` resolution is owned by a new, small, standalone component — a **`CommandCapabilityMap`** (exact name an implementation detail; conceptually a resolver, not a registry) — constructed once at composition-root time (`bootstrap.py`), populated by explicit, hand-authored entries, and injected as a collaborator **into the `CapabilityGovernanceCoordinator`** (not directly into `CommandRouter`). `CommandRouter` itself continues to depend on exactly one new seam — the coordinator — exactly as STEP 1 already concluded; it never sees the resolver, the `CapabilityRegistry`, or any of the four governance engines directly.

This is **Option B** (injected resolver/mapping abstraction), with its population mechanism supplied by **Option D**'s insight (bootstrap.py, the project's existing single authoritative wiring point, is where the relationship is declared) — the two are not competing options once "who owns the mapping at runtime" (Option B) is separated from "who declares the mapping's contents" (Option D); STEP 1.1's own investigation shows they are complementary, not alternatives.

**Option A (CommandRouter-owned mapping) is rejected. Option C (Capability-model-owned metadata) is rejected. Option D standing alone (module-owned metadata) is rejected.** Reasons in §3.

This is one clear decision, not a conditional one: STEP 2 must implement a new resolver class, populated only in `bootstrap.py`, injected only into the coordinator.

## 3. Rejected Alternatives

**Option A — CommandRouter-owned mapping.** Rejected. Would require `CommandRouter` itself to hold `(module, action) → capability_id` state, directly violating criterion 14 ("clear separation between command routing and governance") — `CommandRouter`'s own docstring already defines its responsibilities as parsing, module lookup, and delegation only; owning a governance-specific mapping is a second responsibility bolted onto a class whose entire existing design (`Protocol`-based extensibility, "never needs to change to support new command namespaces") is built around *not* knowing about namespace-specific concerns. Also directly forbidden by hard rule 3 for STEP 2 to implement without amending this task's own constraints.

**Option B — Injected resolver/mapping service.** **Selected**, with the qualification in §1 (injected into the coordinator, not into `CommandRouter` directly) — see §4/§5.

**Option C — Capability metadata is authoritative.** Rejected. `Capability` (EP-069.4) has no routing-identity field today, and hard rule 7 forbids adding one. Independently, even absent that rule, this would be architecturally wrong: `Capability` is deliberately backend-kind-agnostic (`INTERNAL`/`LOCAL_CLI`/`REST_API`/`BROWSER_SERVICE`) and reused across four kinds of executable target — baking `CommandRouter`-specific `(module, action)` fields into it would special-case one backend kind (`INTERNAL`, CLI-command-shaped) inside a model designed to describe all four uniformly, which `EP069_4_DESIGN.md` itself (§15.1's own framing, "proof of fit, not shipped wiring") never proposed and would arguably regress.

**Option D — Module/action registration is authoritative (standing alone).** Rejected as a **complete** solution, retained as a **partial** insight (§1). Standing alone, it would require every existing `CommandModule` implementation (`SystemModule`, `FileModule`, `BrowserModule`, ~20+ others) to gain new capability-declaring surface — either a new `Protocol` member (requires editing `command_router.py`'s `CommandModule` definition, forbidden by hard rule 3) or per-module changes to ~20+ files (a scope expansion no evidence justifies — actions today are interpreted ad hoc inside each module's own `execute()` body via string comparison, not declared anywhere, per `SystemModule`'s `HELP_TEXT` being free text rather than structured data). What *is* retained from Option D: `bootstrap.py` is already the repository's own authoritative point where routing (`router.register(module)`) and every other cross-cutting concern are wired together — so it is the correct place to *populate* the new resolver, even though the resolver itself is a new, separate object, not a capability derived from the modules' own declarations.

**A separate mapping table (as a bare, ungoverned dict with no owning class)** was considered and rejected as a degenerate, worse version of Option B: an unowned dict floating in `bootstrap.py` with no validation, no duplicate-key protection, and no clear place for the drift-mitigation logic in §4 to live. A small, purpose-built class (even a thin one) is the same amount of new code with a defined contract and a natural home for the validation `_check invariants` described in §4.

## 4. Source-of-Truth Model

- **Owns capability identity:** `CapabilityRegistry` (EP-069.4), unchanged — the sole authority on which `capability_id`s exist, their metadata, and their `enabled` flag. Unmodified by this EP.
- **Owns command identity:** `CommandRouter._modules` (module namespace) plus each module's own internal `action` string interpretation, unchanged — `CommandRouter` remains the sole authority on which `(module, action)` pairs are dispatchable at all (i.e., "unknown module" is still decided exactly as today, before governance ever runs).
- **Owns the relationship between them:** the new `CommandCapabilityMap` — and *only* this component. It is intentionally the **sole** source of truth for the relationship itself; neither `CapabilityRegistry` nor `CommandRouter` gains any awareness of the other's identifiers.
- **Who creates/registers the relationship:** `bootstrap.py`, at the same composition-root moment it already registers modules and would already construct the `CapabilityGovernanceCoordinator`'s other collaborators (STEP 1 §10). Entries are explicit and hand-authored — e.g. conceptually `resolver.map("file", "delete", capability_id="file.delete")` — never derived reflectively from module structure (no such structure exists to derive from, per §2/§3's Option D finding).
- **How consistency is guaranteed:** not by construction alone (a hand-authored table can always drift — see Drift Analysis below), but by **two independent, cheap safeguards**, both new, both scoped to STEP 2:
  1. **Eager, startup-time validation** (`DECISION`, not yet repository-precedented, justified below): immediately after `bootstrap.py` populates both the `CapabilityRegistry` and the `CommandCapabilityMap`, a one-time check confirms every `capability_id` the resolver references actually exists in the registry, and raises loudly at startup (matching the existing fail-fast precedent already used for configuration errors — `EmbeddingConfigurationError`, `EP059`-era `OSError` — VERIFIED, `bootstrap.py` already raises eagerly for other misconfiguration classes at this same phase) rather than allowing a silent per-dispatch failure to be the first signal. This is new logic `CommandCapabilityMap` (or a small helper `bootstrap.py` calls once) owns; it is not a change to `CapabilityRegistry` itself.
  2. **Fail-closed at runtime for any drift that startup validation cannot catch** (e.g. a capability later unregistered from `CapabilityRegistry` after startup, if that ever becomes possible — currently VERIFIED to be structurally impossible in production since nothing calls `CapabilityRegistry.unregister()` in `bootstrap.py`, but the coordinator must not assume that remains true forever) — this is the "mapping exists + capability missing → fail closed" semantic already mandated (§ Governance Semantics below), and it is the coordinator's own existing responsibility from STEP 1 §11, unchanged here.
- **What happens when the relationship is missing:** ungoverned — dispatch proceeds exactly as today (§5).
- **What happens when the relationship is inconsistent** (present in the map, absent/mismatched in the registry): fail closed (§5), per the explicit governance semantics this task restates as mandatory.

### Drift Analysis

| Drift scenario | Can it occur? | Consequence under this architecture |
|---|---|---|
| Mapping exists, capability does not (id typo, capability never registered, or removed later) | Yes — a hand-authored table can always contain a typo or reference a capability that was renamed | **Caught at startup** by the eager validation check (fails loudly before Jarvis ever accepts a command), or — if somehow introduced after startup — caught at dispatch time by the coordinator's existing fail-closed rule (STEP 1 §11 step 1, unchanged). Never silently ungoverned. |
| Capability exists, mapping points "elsewhere" (two different `(module, action)` keys map to the same `capability_id`) | Yes, and this is **not necessarily an error** — two distinct commands may legitimately share one governed capability (e.g. two CLI spellings of the same underlying action). Left as a valid pattern; not flagged as drift. | No special handling required. |
| Module/action changes (renamed) without the mapping being updated | Yes — a purely hand-authored table cannot detect a rename in the module's own `execute()` logic, since no structural link exists (§3, Option D rejection) | The renamed action no longer matches any map key, so resolution returns "no capability" for the *new* action string → **silently reverts to the ungoverned path**. This is the one drift class this architecture does **not** fail closed on, and it must be named as a residual, process-level risk (§9), mitigated only by STEP 2 test coverage asserting that every map entry's `(module, action)` still round-trips through a live `CommandRouter` (i.e., the module is still registered and the action string is still one the module's own tests exercise) — a review-time/test-time safeguard, not a structural one, because no structural fix is available without editing `command_router.py`'s `CommandModule` protocol (forbidden). |
| Capability ID changes without the mapping being updated | Same as row 1 — fails closed, either at startup or at dispatch. | Safe. |
| Stale mapping survives capability removal | Same as row 1. | Safe. |
| Duplicate capability mappings (same `(module, action)` key registered twice) | Structurally prevented by construction: `CommandCapabilityMap`'s own registration method raises on a duplicate key, mirroring `CapabilityRegistry.register()`'s and `ToolRegistry.register()`'s own existing duplicate-id-raises convention (**VERIFIED** pattern, both files re-read this session). | Prevented, not merely detected. |
| Different commands accidentally resolve to the same capability (typo collision, not intentional sharing) | Possible in principle (a typo in one map entry happens to equal another's intended id) | Not distinguishable from the legitimate "two commands, one capability" case by the architecture alone; mitigated only by code review of the (small, hand-authored, STEP-2-scoped) map contents — named explicitly as a residual, non-structural risk (§9), same category as the rename case above. |

## 5. Runtime Resolution Flow

```
CommandRouter.dispatch(raw_input)
        │  tokenize -> (module_name, action, arguments)         [UNCHANGED]
        ▼
self._modules[module_name.lower()]  ── not found ──▶ CommandResult(success=False, "Unknown module")  [UNCHANGED]
        │  found
        ▼
coordinator is None?  ── yes ──▶ module.execute(action, arguments)   [UNCHANGED — no governance configured]
        │  no
        ▼
CapabilityGovernanceCoordinator.authorize_dispatch(module_name, action)
        │
        ▼
   [internal] CommandCapabilityMap.resolve(module_name, action) -> capability_id | None
        │
        ├── None (no relationship declared) ─────────────────▶ UNGOVERNED
        │                                                        → module.execute(action, arguments)
        │                                                          [byte-for-byte today's behavior]
        │
        └── capability_id found ─────────────────────────────▶ GOVERNED
                    │
                    ▼
             CapabilityRegistry.find(capability_id)
                    │
                    ├── None (mapping/registry drift) ────────▶ FAIL CLOSED
                    │                                             → CommandResult(success=False,
                    │                                               "governance inconsistency")
                    │                                             → module.execute() NEVER called
                    │
                    └── Capability found ──────────────────────▶ run STEP 1 §11 decision flow
                                │                                  (lifecycle → security → policy)
                                │
                                ├── internal engine error ─────▶ FAIL CLOSED (STEP 1 §12, unchanged)
                                │
                                ├── PolicyLevel != EXECUTE ─────▶ DENY
                                │                                  → CommandResult(success=False,
                                │                                    naming level + reasons)
                                │                                  → module.execute() NEVER called
                                │
                                └── PolicyLevel == EXECUTE ─────▶ ALLOW
                                                                    → module.execute(action, arguments)
                                                                      [UNCHANGED call, now gated]
```

Five distinct outcomes are visible in this diagram, matching the task's own required distinctions: **ungoverned**, **governed + missing capability (fail closed)**, **governed + policy denial**, **governed + internal governance error (fail closed)**, **governed + allowed**.

## 6. Governance Boundary

| Concern | Owner | Changed by EP-069.8? |
|---|---|---|
| What a capability *is* (schema, trust level, permissions, enabled flag) | `CapabilityRegistry` / `Capability` (EP-069.4) | No |
| Fuzzy task-text → ranked candidates | `CapabilityDiscoveryEngine` (EP-069.5) | No — and not consumed by this EP at all (§7) |
| Advisory risk assessment of one capability | `CapabilitySecurityEngine` (EP-069.6) | No |
| Deterministic policy-level decision | `PolicyEngine` (EP-070) | No |
| Lifecycle status / audit history | `CapabilityLifecycleRegistry` (EP-069.7) | No |
| **Whether a `(module, action)` pair *has* a governed capability at all** | `CommandCapabilityMap` (**new**, owned by EP-069.8) | New |
| **Orchestrating resolver + the four engines into one allow/deny outcome for one dispatch** | `CapabilityGovernanceCoordinator` (**new**, owned by EP-069.8) | New |
| Whether an already-resolved dispatch is allowed to reach `module.execute()` | `CommandRouter` (gains one new, optional call site) | Additive only |

No responsibility overlap is introduced: the two new components each own exactly one narrow question ("is there a mapping?" / "given a capability, is it authorized?") that no existing component owns or claims to own.

## 7. Secondary Decisions

**Lifecycle execution audit (STEP 1 Open Question 2):** **DECISION** — do not add any new method to `CapabilityLifecycleRegistry`. Its own module docstring (re-read this session) is explicit: it is "a single, concrete, thread-safe, in-memory tracker of capability lifecycle status and history," with a fixed, closed set of transition methods (`register`/`update`/`disable`/`enable`/`revoke`), each representing a *status* transition. A successful `EXECUTE` authorization is not a status transition — logging "this ran" alongside "this changed state" would conflate two different kinds of record inside a package whose own STEP-3 audit (`EP070_STEP3_AUDIT.md`) already praises its narrow, single-purpose scope. Execution audit (both allow and deny outcomes) belongs to the coordinator's own `loguru` logging, mirroring the convention every existing package in this repository already uses for its own lifecycle events (`CapabilityRegistry.register()` already does `logger.info(f"Capability registered: '{capability.id}'.")` — **VERIFIED**, re-read this session). This preserves EP-069.7's boundary exactly as the task instructs.

**`capability_governance.enabled` (STEP 1 Open Question 3):** **DECISION** — not required for STEP 2. The empty-catalog-by-default behavior (nothing in `CapabilityRegistry` today, and `CommandCapabilityMap` starts with zero entries unless `bootstrap.py` explicitly adds some) already provides complete, structural, backward-compatible safety with no configuration at all — a `coordinator=None` default plus an empty map produces identical behavior to a config flag set to `false`. Adding a config flag on top of an already-safe default would be exactly the "configuration merely for theoretical flexibility" this task instructs against. **This may be revisited by a future EP** once real capabilities are actually registered and an operator-facing kill switch becomes operationally meaningful — but that is a future decision, not a STEP 2 requirement.

**Default trust/policy posture (STEP 1 Open Question 4):** **DECISION** — out of scope for EP-069.8, confirmed again this session. `PolicyEngine`'s six-row table (EP-070, unchanged) already fully determines outcomes from whatever `Capability`/assessment/lifecycle-status values it is given; EP-069.8 introduces no new default and makes no choice about what trust level or permissions a *newly registered* capability should carry — that is a property of whoever registers a capability into `CapabilityRegistry` (a data-population decision, explicitly named in STEP 1 §17 as belonging to a different, future EP). This resolution report does not narrow that further.

**Discovery Engine runtime participation:** **CONFIRMED, not overturned.** Re-verified this session (§2): `CapabilityDiscoveryEngine.discover(task: str, ...)` takes a free-text task description and returns ranked, fuzzy-matched candidates — a fundamentally different input shape from `CommandRouter.dispatch()`'s already-exact `(module_name, action)` pair. There is no scenario in the CommandRouter dispatch path where "rank several plausible candidates" is the right operation — the target is already known precisely, or it is not dispatchable at all (unknown module, handled before governance runs). Discovery remains entirely outside the enforcement chain, exactly as STEP 1 concluded.

**Tool Engine runtime participation:** **CONFIRMED, not overturned.** Re-verified this session (§2): zero references either direction between `command_router.py` and `tool_engine.py`/`tool_manager.py`, and zero `CommandModule` implementation calls `ToolEngine`. They remain two structurally separate execution paths reached by different callers (`CommandRouter.dispatch()` reached by `InteractiveShell`/`ApiRouter`; `ToolEngine.invoke()`/`invoke_for_step()` reached only by `ToolExecutionProvider` from Plan Execution). Integrating `ToolEngine` would require inventing a second enforcement chokepoint with its own resolver, duplicating exactly the machinery this report defines for `CommandRouter` — no repository evidence justifies that duplication now, and doing so would violate criterion 13 ("no unnecessary integration with Tool Engine"). Actions reachable only through `ToolEngine` remain ungoverned after EP-069.8, an explicit, named scope boundary (unchanged from STEP 1 §9).

## 8. STEP 2 Contract

**Files likely to be added:**
- `src/core/capability_governance/__init__.py`
- `src/core/capability_governance/capability_governance_coordinator.py` — `CapabilityGovernanceCoordinator`, its result type, and its own minimal exception root.
- `src/core/capability_governance/command_capability_map.py` — `CommandCapabilityMap`, holding the `(module_name.lower(), action.lower()) → capability_id` relationship, with a `register`/`map` method (raises on duplicate key, mirroring `CapabilityRegistry.register()`'s convention) and a `resolve(module_name, action) -> str | None` method (never raises — mirrors `CapabilityRegistry.find()`'s / `ToolRegistry.find_for_step()`'s "return None, don't raise" convention for the common/negative case).
- `tests/EP069_8/__init__.py` and `tests/EP069_8/test_capability_governance_coordinator.py` (+ a resolver-focused test module), registered in `src/modules/test_module.py` following the existing per-EP registration convention (`EP070_STEP3_AUDIT.md`'s own confirmed precedent).

**Files likely to be modified:**
- `src/core/command_router.py` — add one optional constructor parameter (`coordinator: CapabilityGovernanceCoordinator | None = None`) and the single new call site inside `dispatch()`, exactly at the point in §5's diagram. No other change to this file.
- `src/bootstrap.py` — construct `CapabilityRegistry`, `CapabilitySecurityEngine`, `PolicyEngine`, `CapabilityLifecycleRegistry`, `CommandCapabilityMap` (populated with zero or more explicit entries — zero is a fully valid STEP 2 outcome, per §7's config decision), run the one-time startup validation (§4), construct `CapabilityGovernanceCoordinator` from all of the above, and pass it into `CommandRouter(...)`.
- No file under `src/core/capability/`, `src/core/capability_discovery/`, `src/core/capability_security/`, `src/core/capability_policy/`, or `src/core/capability_lifecycle/` is modified.

**Interfaces/classes required:** `CommandCapabilityMap` (new), `CapabilityGovernanceCoordinator` (new), plus whatever small result type the coordinator returns (e.g. wrapping `PolicyDecision` with a resolved boolean, per STEP 1 §10 — unchanged by this report).

**Dependency injection direction:** `bootstrap.py` constructs everything and injects downward: `CommandCapabilityMap` and the four engines → into `CapabilityGovernanceCoordinator` → into `CommandRouter`. Nothing is constructed inside `CommandRouter` or inside the coordinator itself; both receive fully-built collaborators only, matching this project's own established Dependency Policy (already cited in `tool.py`'s own docstring: "never instantiate large services inside business logic").

**Mapping/resolution mechanism:** hand-authored `CommandCapabilityMap` entries, added explicitly in `bootstrap.py`, validated eagerly at startup against `CapabilityRegistry` contents (§4). No reflective/automatic derivation from `CommandModule` structure (none exists to derive from).

**Fail-open vs. fail-closed:** No relationship declared → **pass through unchanged** (this is not "fail open" in the security sense — it is "not governed," identical to today's actual behavior, not a weakened check). Relationship declared but capability/engine outcome is anything other than a clean `EXECUTE` → **fail closed** in every case (missing capability, non-`EXECUTE` policy level, internal engine exception). This is unchanged from STEP 1 and is restated here because the task requires it to be explicit.

**Required tests:** unchanged from STEP 1 §16, plus new resolver-specific cases: duplicate-key registration raises; `resolve()` returns `None` for an unmapped pair without raising; startup validation raises when a mapped `capability_id` is absent from `CapabilityRegistry`; a mapped-but-since-removed capability (simulated) is denied, not silently passed through.

**Backward compatibility requirements:** unchanged from STEP 1 §13 — `CommandRouter()` with no `coordinator` argument, and a `CommandRouter(coordinator=...)` where the coordinator's `CommandCapabilityMap` is empty, must both reproduce today's exact `dispatch()` behavior for every currently registered module/action.

## 9. Remaining Blocking Questions

None of the primary resolution mechanism is blocked. Two residual, **non-blocking** risks are named explicitly (both from the Drift Analysis, §4) and must be carried into STEP 2 as documented, reviewed-not-structurally-prevented risks, not as unresolved architecture:

- Module/action rename silently reverting a governed command to ungoverned (no structural detection possible without editing `command_router.py`'s `CommandModule` protocol, which remains out of scope).
- Accidental capability_id collision between two unrelated map entries (mitigated by code review only, since it is indistinguishable from intentional capability-sharing by the architecture itself).

Neither prevents STEP 2 from proceeding; both are addressed by test coverage and review discipline named in §8, not by further architectural decisions.

`No architectural blockers remain for STEP 2.`
